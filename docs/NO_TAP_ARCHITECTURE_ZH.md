# WEL 无虚拟网卡网络架构与实测基准

> 更新日期：2026-08-18
> 适用仓库：`wel-no-tap`
> 当前阶段：P2 鉴权云中继已完成搜索、加入、开赛和至少 10 分钟比赛验证；P3 libjuice ICE 已按真实比赛对手建立直连，并保留中继回退
> 现网关系：本项目独立于 `welopenvpn-clean`，不会替换或改动当前 TAP/n2n 平台

## 1. 文档用途

本文是无虚拟网卡方案的权威开发基准，只记录代码、真实局域网追踪、双机联机
和云中继日志已经证实的事实。后续开发应以本文中的 Socket 时间线、数据报边界、
逻辑端口分流和中继对账规则为准。

项目目标是在不安装 TAP-Windows、OpenVPN、n2n、WinDivert、系统路由或虚拟 IP
的前提下，让 WE8 完成搜索、加入和比赛。平台只透明搬运原始 UDP 数据报，不
解析传球、比分、阵型或游戏状态。

## 2. 已确认的 WE8 Socket 行为

### 2.1 实际调用范围

本次测试的 32 位 WE8 构建实际观察到：

```text
socket
bind
sendto
recvfrom
closesocket
```

未观察到：

```text
select
WSAEventSelect
WSAAsyncSelect
WSAWaitForMultipleEvents
WSAPoll
WSASendTo
WSARecvFrom
```

当前 WE8 约每 `15-16 ms` 主动轮询一次非阻塞 `recvfrom`：

- 接收队列为空：返回 `SOCKET_ERROR / WSAEWOULDBLOCK (10035)`。
- 队列有包：一次返回一个完整 UDP 数据报及其来源地址。
- 句柄无效：保持原生 Winsock 行为，返回 `10038`。

因此对这个已测试构建，虚拟化独立 Socket 接收队列和 `recvfrom` 已足够触发
接收，不需要伪造 `select` 或事件就绪通知。若以后更换 WE8 构建，必须重新追踪
API，不能直接外推。

### 2.2 完整联机协议

```text
搜索：
  客机搜索 Socket 随机端口 -> 255.255.255.255:5739  24 字节
  主机 5739 -> 客机原搜索端口                       136 字节

加入：
  客机新建另一个 Socket
  客机加入随机端口 -> 主机 5739                     64 字节
  未接受前约每 3 秒重发

接受：
  主机新建临时 Socket
  主机临时随机端口 -> 客机加入端口                  84 字节
  发送后立即关闭临时 Socket

比赛：
  客机加入随机端口 <-> 主机 5739
  持续双向 UDP，必须保持每个数据报的边界和来源端口
```

关键约束：

1. 搜索 Socket 与加入 Socket 不是同一个 Socket，随机端口不同。
2. 主机固定监听 `5739`，但接受包来自主机临时随机端口。
3. 不能把所有流量规整为 `5739 -> 5739`。
4. 接收端必须按目标逻辑端口投递到准确的游戏 Socket。
5. 原始 WE8 载荷不能合并、拆分、截断或修改。

## 3. 从真实局域网到无网卡实现

### 3.1 真实局域网基准

成功的真实局域网追踪先确认了完整时间线：

```text
搜索：192.168.3.89:51440 -> 255.255.255.255:5739，24 字节
回复：192.168.3.124:5739 -> 192.168.3.89:51440，136 字节
加入：客机 :65396 -> 主机 :5739，64 字节
接受：主机 :53228 -> 客机 :65396，84 字节后关闭临时 Socket
比赛：客机 :65396 <-> 主机 :5739
```

这份追踪的用途是定义 WE8 需要看到的 Socket 语义，不是让新方案复制真实局域网
地址或依赖操作系统路由。

### 3.2 P1 局域网无网卡实测

P1 在两台电脑上完全移除虚拟网卡数据面，仅用用户态虚拟 Socket 与局域网中继，
成功完成搜索、加入和约 4 分钟比赛：

```text
搜索端口：56350
加入端口：56351
主机临时接受端口：50244

主机发送 / 客机接收：4626 包，1,240,641 字节
客机发送 / 主机接收：3506 包，  202,078 字节
Hook 接收队列丢弃：0
```

这证明以下能力已经实际跑通，而不是设计推测：

- 每个 WE8 Socket 的逻辑 IP、逻辑端口和生命周期映射。
- 搜索广播按房间扇出。
- `24/136` 字节搜索往返。
- 新加入随机端口和 `64` 字节加入请求。
- 主机临时随机端口的 `84` 字节接受包。
- 比赛阶段持续双向 UDP 和数据报边界保持。

结论是：WE8 不要求 Windows 真正拥有逻辑 IP。只要 Hook 返回与局域网一致的
Socket 结果，游戏就能把对端视为可搜索、可加入的网络节点。

## 4. 当前 P2 架构

### 4.1 房间模式硬隔离

Go API 通过 `connection_mode` 将四个房间分成两条独立流程：

| 房间 | 网段 | 模式 | 行为 |
|---|---|---|---|
| 直连 01 | `10.122.1.0/24` | `direct` | candidate 发布完成后进入；比赛优先直连，中继兜底 |
| 直连 02 | `10.122.2.0/24` | `direct` | 同上 |
| 中继 03 | `10.122.3.0/24` | `relay` | 不启动 ICE、不发布 candidate、不做直连信令 |
| 中继 04 | `10.122.4.0/24` | `relay` | 同上 |

中继房间的 ICE 接口由服务端拒绝，避免异常客户端混用两种模式。两种房间都保留
`welnpt.dll` Hook，因为搜索广播、加入包和比赛 UDP 的虚拟 Socket 搬运仍依赖 Hook。

直连房间进入顺序为：申请临时租约，启动 `welnptice.exe`，等待至少一个有效
candidate，向 Go 发布 SDP，最后才显示正式进入并启动成员轮询和心跳。任何一步失败
都会清理 ICE 并释放临时租约，不能以“仅中继”状态混入直连房间。

每次 Hook 识别到新的比赛事务，都必须按真实对手逻辑 IP 重新协商；旧比赛的 remote
SDP、target 和 agent 状态不得复用。直连在有效窗口内失败后，本场锁定云中继，不能
阻塞搜索、加入或比赛。后续 A/B/C 预热池的边界是：A 服务当前场，B 后台收集，下一场
激活 B 后再准备 C；备用 agent 在显式激活前不得向 Hook 发送控制消息。

```text
WE8.exe
  -> welnpt.dll 虚拟 UDP Socket 层
  -> 每个玩家一个真实物理 UDP transport Socket
  -> 22333/UDP 鉴权云中继
  -> 对端 transport Socket
  -> 对端每个逻辑 Socket 的 FIFO 接收队列
  -> 合成 recvfrom 返回值交给对端 WE8.exe
```

该架构不使用：

- TAP、n2n、OpenVPN 或其他虚拟网卡。
- WinDivert、WFP 驱动或内核抓包驱动。
- Windows ARP、房间路由或系统虚拟 IP。
- 玩家侧 WE8 公网入站端口。

双方只维护一个发往云中继的 UDP 出站/NAT 映射。中心中继是可靠性基线，P2P
只能作为以后降低延迟和带宽成本的优化；P2P 失败必须能继续使用中继。

## 5. 虚拟 Socket 契约

### 5.1 生命周期与地址

Hook 跟踪 WE8 创建的每个 IPv4 UDP Socket：

- `bind(...:5739)` 只记录逻辑监听端口，不在物理网卡真实监听 `5739`。
- 未显式绑定的 Socket 在首次收发前分配 `49152-65535` 逻辑随机端口。
- `getsockname` 返回本玩家逻辑 IP 和当前 Socket 的逻辑端口。
- `closesocket` 删除映射并释放该 Socket 尚未消费的队列。
- 不属于虚拟表的句柄交回原始 Winsock，保持系统错误码。

逻辑 IP 只存在于 Hook、协议头和房间成员表中，不出现在 `ipconfig`、设备管理器、
ARP 表或 Windows 路由表中。

### 5.2 出站

每次 `sendto` 必须作为一个独立中继数据报发送，并保留：

```text
房间
来源逻辑 IP 和来源逻辑端口
目标逻辑 IP 和目标端口
广播标志
原始载荷长度与原始载荷
诊断序号
```

中继 transport 成功接收封装后，Hook 向 WE8 返回原始载荷长度。搜索广播发送给
同房间其他成员；逻辑单播只发送给目标逻辑 IP。

### 5.3 入站

transport 线程校验中继包后，根据目标逻辑端口查找本地 WE8 Socket，并把一个
完整数据报加入其 FIFO 队列。WE8 调用 `recvfrom` 时：

- 队列非空：返回原始载荷，并合成远端逻辑 IP 和原始逻辑源端口。
- 队列为空：返回 `SOCKET_ERROR / 10035`。
- 目标 Socket 已关闭或不存在：记录本地 `relay-drop`，不投递给其他 Socket。

`relay-drop` 这个历史字段名容易误解。它表示 DLL 收到中继包后无法加入目标
逻辑 Socket 队列，常见原因是 Socket 已关闭；它不等同于 Linux 中继丢包。

实现保留同步 `WSASendTo/WSARecvFrom` 的防御性兼容。当前已测试 WE8 没有使用
它们；重叠 I/O 当前也不属于已验证路径。

## 6. 中继协议 v2

P2 使用固定 `74` 字节头部，整数、地址和端口均为网络字节序：

```text
magic[4] = WNP2
version[1]
type[1] = register | data
flags[1] = broadcast
reserved[1]
room[32]
sourceIPv4[4]
sourcePort[2]
targetIPv4[4]
targetPort[2]
payloadLength[2]
sequence[4]
authTag[16] = HMAC-SHA256 前 16 字节
payload[n]
```

中继按 `(room, logical IP)` 保存玩家的真实 UDP endpoint，客户端每 2 秒注册一次，
30 秒无活动则淘汰。每个注册包和数据包必须通过 HMAC 校验；失败包直接丢弃。

最初 P2 实测使用双方相同的私有测试令牌。当前客户端已改为先用 Laravel 账号密码
登录 Go API，再由独立 No-TAP 控制器下发房间、中继、逻辑 IP 和中继密钥。当前
下发的仍是部署级共享中继密钥，不是最终的玩家级短期凭证；后续仍需增加防重放、
速率限制和带宽配额。当前协议提供认证与完整性校验，但不加密 WE8 载荷。

### 7.3 尾段 `relay-drop` 的正确解释

客机日志尾部出现：

```text
46 个 relay-drop
合计 13,040 字节
目标逻辑端口全部为 63540
```

这 46 条全部出现在客机有效 Socket 活动停止后的日志尾部，表示晚到的主机数据
已经找不到仍可消费的客机逻辑 Socket。用户确认本次已经完成完整十分钟比赛，
并且双方是在游戏内正常结束比赛后停止测试。因此这些属于正常退出阶段的尾包，
不能据此认定 Linux 中继丢包，也不能把它算作比赛期间的传输丢包。

因此本样本可以得出：

- 云中继搜索成功。
- 云中继加入和接受成功。
- 比赛流量成功开始。
- 完整比赛持续至少 10 分钟。
- 双方在游戏内正常结束，退出阶段尾包行为符合预期。

### 7.4 当前平台集成

历史 P2 配置用于证明数据面可行，当前控制面已切换为独立的 No-TAP 房间体系：


客户端不能进入同一房间，也不能消费对方的租约或 IP 段。

### 7.5 多人房间中的 P2P 对手选择

房间候选只表示玩家具备直连条件，不能把成员列表中的第一个候选当作比赛对手。
当前实现按已经验证的 WE8 协议阶段选择目标：

```text
搜索：24 字节广播 + 136 字节单播回复       不选择比赛对手
加入：客机 64 字节 -> 主机逻辑端口 5739   双方锁定彼此逻辑 IP
比赛：只把该逻辑 IP 的单播切换到 ICE       其他流量继续使用中继
```

因此房间有 100 人时，A/B、C/D、E/F 可以各自同时建立独立的双向 ICE 通道，
每个客户端只维护自己当前一场比赛的正式直连，不会与全部房间成员建连接。
ICE 尚未完成或失败时，数据继续走云中继，不阻塞搜索、加入或比赛。

玩家详情只 Ping 中继服务器和中继玩家，不启动临时 ICE Agent。中继玩家 Ping 始终
携带被点击玩家的逻辑 IP，由中继只路由到对应诊断端点。比赛级 ICE 只在真实比赛
对手被 Hook 识别后建立，不会被详情 Ping 改变或占用。

## 9. 诊断日志判读

每次测试必须同时保留主机和客机 JSONL，先按逻辑端口和数据长度对账：

1. 客机是否发出目标 `5739` 的 24 字节搜索包。
2. 主机是否收到同源端口 24 字节包并回复 136 字节。
3. 客机是否创建新的加入端口并发送 64 字节。
4. 主机是否从临时随机端口发出 84 字节接受包。
5. 客机是否从该临时端口收到 84 字节。
6. 比赛端口与主机 `5739` 是否开始持续双向交换。
7. 双方 `sendto` 与对端 `recvfrom` 的包数和字节数是否能在重叠时间窗对账。
8. `relay-drop` 是出现在有效比赛期间还是 Socket 关闭后的尾部。
9. 服务端 `auth_drops`、`malformed_drops`、`route_drops` 是否增长。

不能只看到一个错误字段就判断根因。必须先区分：游戏没有发送、客户端没有封装、
中继没有路由、对端没有收到，还是对端 Socket 已关闭后晚包到达。

4. 比赛持续至少 10 分钟。
5. 双方正常退出后再结束日志。
6. 同时提交两份 JSONL，并对账有效时间窗内所有 `sendto/recvfrom`。

P2 已通过当前这组公网十分钟比赛验收，但仍需完成更多网络环境和安全能力测试，
才能替换现网生产平台。现有 TAP/n2n 继续承担生产联机；无网卡版本在独立仓库
继续成熟。

## 11. 当前已经验证的直连结论

### 11.1 直连不是 candidate 出现就算成功

房间进入时客户端会启动 `welnptice.exe`，通过 STUN 收集本机 candidate，并把
candidate 发布给 Go API。候选数量只能说明“具备尝试条件”，不能说明两台电脑已经
互通。只有 libjuice 状态进入 `connected` 或 `completed`，并且游戏单播日志出现
`path:"direct"`，才可以判定比赛流量已经切换到 P2P。

房间进入不等待 ICE 完整收集。客户端先加入房间并启用中继，随后后台启动 ICE
组件并发布候选；候选收集失败只代表直连优化不可用，不影响搜索、加入或中继比赛。
正式 `welnptice.exe` agent 使用 IPv4 wildcard (`0.0.0.0`) 绑定，因为 WE8 是 IPv4
UDP 游戏，这会避开 Win7 Teredo/IPv6 隧道适配器造成的无效候选和长时间 STUN 超时。
它不会绑定或改变游戏的中继 Socket，也不会影响 Hook 搜索广播。

正确的状态顺序是：

```text
直连候选收集 -> 双方交换 SDP -> ICE connectivity check
-> connected/completed -> 锁定游戏对手 -> 实际单播走 direct
```

搜索广播不会切换到直连。广播仍走云中继，因为 ICE 直连只针对已经确认的两名
比赛对手，不能把一个房间内的广播错误地发给某个候选玩家。

### 11.2 最新比赛日志已确认真实直连

一次完整会话日志中出现了以下有效顺序：

```text
direct-state: connecting
direct-target: 10.122.1.13
真实加入包：relay 单播 64 字节
direct-state: connected
direct-state: completed
比赛单播：transport-recv/sendto path:"direct"
```

该会话随后有数千个直连收发包。玩家直接退出客户端后，约一段超时等待后出现
`direct-state: failed`，这是对端消失后的 ICE 超时，不是比赛期间直连失败。判断
失败必须结合最后一个有效 `path:"direct"` 数据包和退出时间，不能只看文件最后一行。

### 11.3 多人房间支持多条独立比赛直连

房间内有 100 人时，不是一个客户端与全部玩家建立 ICE。游戏真正发送 `64` 字节
加入包后，Hook 报告该包对应的逻辑 IP，客户端只锁定这一名对手。识别条件不能写死
目标端口为 `5739`：主机接收加入包时目标端口可能是 `5739`，客机主动发送加入包时
目标端口通常是主机当前的动态游戏端口。两种方向都必须按真实加入包识别：

```text
A <-> B  一条正式 ICE 通道
C <-> D  另一条正式 ICE 通道
E <-> F  另一条正式 ICE 通道
```

每个客户端只维护自己当前比赛的正式对手。其他成员继续留在房间列表中，不会被
错误地当作游戏对手，也不会因为候选列表排序变化而切错通道。

### 11.4 玩家详情 Ping 与比赛直连隔离

玩家详情 Ping 只检查中继服务器和中继玩家，不再创建临时 ICE Agent，也不执行直连
connectivity check。中继 Ping 携带目标玩家的逻辑 IP，由中继精确转发到目标玩家。
比赛级 ICE 只在 Hook 识别出真实加入对手后按本场事务建立，不能被详情 Ping 占用、
重启或关闭。

因此：

- Ping 某个玩家不应该改变之后的比赛对手选择。
- 房间人数增加后，中继 Ping 仍必须按点击的目标用户 ID 定向。
- 是否直连只以真实比赛的 ICE 状态和游戏单播日志为准。

### 11.5 搜索和中继是功能底线，ICE 只是优化

无网卡版的优先级必须固定如下，后续任何性能或直连改动都不能颠倒它：

```text
第一优先级：客机能搜索到已经建主的主机
第二优先级：搜索、加入、接受和比赛单播始终可走 22333/UDP 云中继
第三优先级：在当前两名比赛对手确实互通时，把比赛单播优化为 P2P 直连
```

具体边界：

- `24` 字节搜索广播和 `136` 字节搜索回复始终通过房间中继扇出，绝不能交给
  ICE，也不能因为 candidate 收集、ICE 超时或防火墙规则检查而停止。
- `64` 字节加入和 `84` 字节接受始终走中继，用于识别对手并保证联机界面可继续。
- 新场开始后路径处于待选择状态。ICE 尚未完成时，正式比赛单播先由中继托底，但不
  因固定短超时永久判定本场只能中继。ICE 随后进入 `connected`/`completed` 时，本场
  只升级一次到 `path:"direct"`。这是 `v0.0.22` 已验证可直连的选择方式，同时避免
  candidate 收集和 API 交换时间超过 2.5 秒时把所有可直连比赛误锁成中继。
- 本场直连发送失败时只允许单向降级并锁定中继，不允许再次升级直连，避免比赛期间
  在两个路径之间来回切换。
- ICE、防火墙规则、STUN、candidate 或玩家详情 Ping 失败都只能降低直连概率，
  不能让玩家搜不到主机，也不能让已经可用的中继比赛失败。

这也是为什么 `v0.0.22` 在没有 ICE 防火墙规则时仍可完成搜索和中继联机：该规则
从来不是搜索或中继的前提，只可能影响 P2P 优化是否可用。

### 11.6 房间、WE8 与单场比赛是三个独立生命周期

不能把“进入房间一次”或“启动 WE8 一次”误当成“只能打一场”。平台必须区分：

```text
房间生命周期：进入房间 -> 退出房间/租约回收
WE8 进程生命周期：启动 WE8 -> 关闭 WE8
比赛连接生命周期：一次真实 64 字节加入 -> 84 字节接受 -> 本场结束/下一次加入
```

同一个 WE8 进程可以完成同一对手的主场和客场，也可以在不关闭游戏的情况下换另一名
对手。因此每次真实加入都要重新确认本场对手；但同一场等待接受期间，WE8 会大约每
3 秒重发相同的 `64` 字节加入包，不能把每个重发包当成新比赛。`64` 字节加入和
`84` 字节接受属于同一场，不能因为接受包再次重建 ICE。实现先用“发起方加入 Socket
的逻辑端口”归一化握手：64 字节取源端口，84 字节取目标端口；同时记录本场是否已经
出现正式比赛数据。正式数据出现后再次收到 64 字节加入，即使同一对手继续复用同一个
Socket 和端口，也会增加场次代次并重新尝试直连。因此主场、客场、换对手、同一 WE8
进程连续比赛都按场次隔离。

当前 Hook 把以下事务标识交给 ICE 控制层：

```text
对手逻辑 IP | 发起方加入 Socket 的逻辑端口 | 本机比赛代次
```

同一事务键表示同一场加入请求，重复包只处理一次，不重建 agent、不反复刷新“正在建立
P2P 直连”的界面。换对手、加入端口变化，或上一场已有正式数据后再次加入，都会增加
本机比赛代次并产生新事务键；此时重建正式 ICE agent、发布新的本场 candidate，并与
准确对手交换 SDP。Hook 在第一次识别新事务时立即清除旧对手和旧直连状态，因此该场
的 `64` 加入和随后 `84` 接受可靠地继续经中继。候选或 API 稍晚到达时，中继继续承载
数据；fresh agent 成功后才单向升级直连。即使上一场协商失败，也视为旧 agent 已被
使用；下一场必须重建，避免复用旧 remote SDP。多个新事务串行重建，旧事务的等待会
在发现对手切换后取消。

libjuice 不支持在同一个 agent 上直接更换远端描述，所以换对手或新比赛的 agent 重建
是必要的。重建只更新本机 Hook 指向的新 helper UDP 端口并清除直连连接态；中继
transport 和虚拟 Socket 队列不重启、不清空，保证协商期间比赛仍可继续经云中继。

### 11.7 ICE 防火墙规则的最小职责

客户端只维护一条程序绑定的入站规则：

```text
名称：WEL No-TAP ICE UDP
方向：入站
动作：允许
协议：UDP
配置文件：全部
程序：当前安装目录的 welnptice.exe
```

规则写入采用静默方式：优先更新已存在的同名规则，找不到时才添加；添加后按短暂延迟
复查，避免 Windows 防火墙服务同步延迟导致“规则已出现但刚写完就被误判缺失”。路径
检查会规范化环境变量和真实文件路径，避免升级、中文目录或短路径形式造成重复创建。

不再创建 WE8 入站、WE8 出站或 ICE 出站规则。它们不是搜索与中继的必要条件，而且
会扩大规则面、增加旧系统兼容问题。ICE 规则无法写入时只记录诊断，不弹窗、不显示
黄色阻塞提示，也不阻止进入房间、启动游戏或中继联机；用户以管理员权限运行客户端可
提高规则写入成功率，但不应成为使用中继的前置条件。

## 12. 已踩过的坑与处理规则

### 12.1 `Start-Process -Wait` 会把游戏子进程一起等住

非管理员启动 WE8 时，如果收到 Windows 740，客户端会用 PowerShell `RunAs` 提权
启动 `welnptgame.exe`。旧实现使用 `Start-Process -Wait`，PowerShell 会继续等待
辅助程序启动的 `WE8.exe`，导致客户端一直处于 loading：刷新按钮转圈、退出房间
按钮灰色、传输状态监控不启动。

当前 `v0.0.23` 已改为只等待辅助程序自身最多 15 秒。Hook 注入完成后立即返回，
游戏继续运行，客户端可以正常退出房间和更新直连状态。不要把 `-Wait` 加回去。

### 12.2 UAC 每次弹出是 Windows 行为

如果 `WE8.exe` 被设置为“必须管理员运行”，普通权限平台每次使用 `RunAs` 启动
游戏都需要一次 UAC 确认。它不是防火墙规则，也不会因为第一次允许就永久记住。
平台本身以管理员运行时，子进程可以继承管理员令牌，通常只在平台启动时确认一次。

### 12.3 32 位 Hook 不能用 64 位构建

实况 8 的 `WE8.exe` 是 32 位进程，因此 `welnpt.dll`、`welnptgame.exe`、
`welnptice.exe` 和 Hook 相关辅助程序必须使用 x86 构建。64 位辅助程序无法向
32 位游戏注入，常见表现是 Windows error 5、error 740 或 Hook 初始化失败。

### 12.4 不要用广播包决定比赛对手

`24` 字节搜索广播和 `136` 字节搜索回复只能证明“可搜索”。多人房间中如果用
第一个收到的广播回复设置 ICE 对端，会产生 A 与错误玩家建立直连、Ping 错人、
比赛退回中继等问题。正式对手只能从真实的 `64` 字节加入请求锁定，而且主客机的
主动发送与被动接收都要识别。目标玩家刚发起加入时，另一端的 candidate 可能尚未
写入 API；客户端必须按这个逻辑 IP 重试读取对应成员，而不能第一次查不到就永久
回退中继。

### 12.5 `relay-drop` 不一定是中继丢包

对端游戏或 Hook Socket 已经关闭后，网络中仍可能有晚到数据。客户端无法把它
放入已关闭的逻辑 Socket 队列时会记录 `relay-drop`。必须用时间线判断它发生在
比赛中还是退出后的尾部，并同时检查 Linux 中继的 `route_drops`。

### 12.6 无网卡房间与 TAP 房间不能混用

```text
无网卡：/api/v1/notap/*，10.122.1.0/24 - 10.122.3.0/24
TAP/n2n：原有房间接口，10.222.x.x
```

两类客户端不能进入对方房间，不能复用租约、逻辑 IP、relay token 或房间数据表。
部署无网卡服务时不能重启或改写现有 TAP/n2n 服务。

### 12.7 无网卡方案没有玩家侧虚拟网卡和系统路由

不能用 `ipconfig`、设备管理器、ARP 表或 Windows 路由表验证无网卡逻辑 IP。它只
存在于 Hook、Go 房间租约、中继封装和游戏返回的 Socket 地址中。客户端也不应安装
TAP、n2n、OpenVPN、WinDivert 或 WFP 驱动。

### 12.8 Laravel 用户管理中的超级管理员保护

Laravel 用户管理固定以 `admin`（可由 `SUPER_ADMIN_USERNAME` 配置）作为超级管理员
账号。普通管理员可以管理其他普通用户，但不能在用户管理中修改 `admin`，也不能
修改自己的管理账号；只有超级管理员本人可以操作 `admin`。普通用户的个人资料
接口仍然独立，不受这条后台用户管理规则影响。

### 12.9 启动辅助程序不能把 WE8 秒退误判为成功

`welnptgame.exe` 完成注入并恢复主线程，只能证明游戏组件加载流程走完，不能证明
`WE8.exe` 已稳定运行。部分 Win7 环境中，游戏可能在恢复后立即退出；如果辅助程序
此时直接返回成功，客户端会短暂显示“游戏已启动”，随后按钮恢复，却没有任何可用
错误信息。

当前启动流程同时等待组件就绪事件和游戏进程：组件就绪前游戏退出会立即失败；恢复
运行后再观察 1.5 秒，期间退出同样判定为失败，并记录 `WE8.exe` 的实际进程退出码。
正常游戏不受影响，客户端只会在“游戏组件加载中”状态多等待这段稳定性确认时间。

## 13. 日志与问题定位顺序

Windows 客户端的比赛会话日志默认在：

```text
%LOCALAPPDATA%\\WELPlatform\\logs\\room-session-*.jsonl
```

每次问题必须同时收集主机和客机日志。按下面顺序定位：

1. 是否有 `hook-ready`、`socket`、`bind logicalPort:5739`。
2. 搜索是否有 `transport-recv/sendto` 的 `broadcast:true`。
3. 是否出现 `direct-target`，目标是否是实际加入的玩家。
4. 是否出现 `direct-state: connected/completed`。
5. 比赛单播是否出现 `path:"direct"`，还是只有 `path:"relay"`。
6. `failed` 是否发生在玩家退出或最后一个数据包之后。
7. 中继端是否增加 `auth_drops`、`malformed_drops`、`route_drops`。

“候选已就绪”“中继服务器 Ping 通”“最后一行 failed”都不能单独证明比赛
线路。必须把 Hook 日志、ICE 状态和实际游戏单播合并判断。

## 14. 生产使用边界

目前已验证：

- 局域网和异地网络的无虚拟网卡搜索、加入和完整比赛。
- 云中继可靠收发和直连失败时的中继回退。
- 直连成功后实际游戏单播切换到 P2P。
- 直连结束后平台状态可以识别退出后的超时尾部。

仍需要持续验收：

- 不同运营商、对称 NAT、企业网络和严格防火墙下的 ICE 成功率。
- Windows 10/11 多网卡、VPN 共存和安全软件拦截。
- 直连服务容量、relay 带宽、玩家级短期凭证、防重放和限速。
- 中继故障转移、监控告警、自动更新以及服务端备份恢复。

因此无网卡版当前可以作为独立测试/灰度平台上线，但不能把直连当成唯一数据面。
中继必须始终保留，直连只是降低延迟和服务器带宽的优化路径。
