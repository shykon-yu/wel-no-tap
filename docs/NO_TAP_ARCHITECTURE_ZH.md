# WEL 无虚拟网卡网络架构与实测基准

> 更新日期：2026-08-14
> 适用仓库：`wel-no-tap`
> 当前阶段：P2 鉴权云中继已完成搜索、加入和开赛验证，尚未完成公网长稳验收
> 现网关系：本项目独立于 `welopenvpn-clean`，不会替换或改动当前 TAP/n2n 平台

## 1. 文档用途

本文是无虚拟网卡方案的权威开发基准，只记录代码、真实局域网追踪、双机联机
和云中继日志已经证实的事实。后续开发应以本文中的 Socket 时间线、数据报边界、
逻辑端口分流和中继对账规则为准。

项目目标是在不安装 TAP-Windows、OpenVPN、n2n、WinDivert、系统路由或虚拟 IP
的前提下，让 WE8 完成搜索、加入和比赛。平台只透明搬运原始 UDP 数据报，不
解析传球、比分、阵型或游戏状态。

## 2. 已确认的 WE8 Socket 行为

### 2.1 实际调用范围

本次测试的 32 位 WE8 构建实际观察到：

```text
socket
bind
sendto
recvfrom
closesocket
```

未观察到：

```text
select
WSAEventSelect
WSAAsyncSelect
WSAWaitForMultipleEvents
WSAPoll
WSASendTo
WSARecvFrom
```

当前 WE8 约每 `15-16 ms` 主动轮询一次非阻塞 `recvfrom`：

- 接收队列为空：返回 `SOCKET_ERROR / WSAEWOULDBLOCK (10035)`。
- 队列有包：一次返回一个完整 UDP 数据报及其来源地址。
- 句柄无效：保持原生 Winsock 行为，返回 `10038`。

因此对这个已测试构建，虚拟化独立 Socket 接收队列和 `recvfrom` 已足够触发
接收，不需要伪造 `select` 或事件就绪通知。若以后更换 WE8 构建，必须重新追踪
API，不能直接外推。

### 2.2 完整联机协议

```text
搜索：
  客机搜索 Socket 随机端口 -> 255.255.255.255:5739  24 字节
  主机 5739 -> 客机原搜索端口                       136 字节

加入：
  客机新建另一个 Socket
  客机加入随机端口 -> 主机 5739                     64 字节
  未接受前约每 3 秒重发

接受：
  主机新建临时 Socket
  主机临时随机端口 -> 客机加入端口                  84 字节
  发送后立即关闭临时 Socket

比赛：
  客机加入随机端口 <-> 主机 5739
  持续双向 UDP，必须保持每个数据报的边界和来源端口
```

关键约束：

1. 搜索 Socket 与加入 Socket 不是同一个 Socket，随机端口不同。
2. 主机固定监听 `5739`，但接受包来自主机临时随机端口。
3. 不能把所有流量规整为 `5739 -> 5739`。
4. 接收端必须按目标逻辑端口投递到准确的游戏 Socket。
5. 原始 WE8 载荷不能合并、拆分、截断或修改。

## 3. 从真实局域网到无网卡实现

### 3.1 真实局域网基准

成功的真实局域网追踪先确认了完整时间线：

```text
搜索：192.168.3.89:51440 -> 255.255.255.255:5739，24 字节
回复：192.168.3.124:5739 -> 192.168.3.89:51440，136 字节
加入：客机 :65396 -> 主机 :5739，64 字节
接受：主机 :53228 -> 客机 :65396，84 字节后关闭临时 Socket
比赛：客机 :65396 <-> 主机 :5739
```

这份追踪的用途是定义 WE8 需要看到的 Socket 语义，不是让新方案复制真实局域网
地址或依赖操作系统路由。

### 3.2 P1 局域网无网卡实测

P1 在两台电脑上完全移除虚拟网卡数据面，仅用用户态虚拟 Socket 与局域网中继，
成功完成搜索、加入和约 4 分钟比赛：

```text
搜索端口：56350
加入端口：56351
主机临时接受端口：50244

主机发送 / 客机接收：4626 包，1,240,641 字节
客机发送 / 主机接收：3506 包，  202,078 字节
Hook 接收队列丢弃：0
```

这证明以下能力已经实际跑通，而不是设计推测：

- 每个 WE8 Socket 的逻辑 IP、逻辑端口和生命周期映射。
- 搜索广播按房间扇出。
- `24/136` 字节搜索往返。
- 新加入随机端口和 `64` 字节加入请求。
- 主机临时随机端口的 `84` 字节接受包。
- 比赛阶段持续双向 UDP 和数据报边界保持。

结论是：WE8 不要求 Windows 真正拥有逻辑 IP。只要 Hook 返回与局域网一致的
Socket 结果，游戏就能把对端视为可搜索、可加入的网络节点。

## 4. 当前 P2 架构

```text
WE8.exe
  -> welnpt.dll 虚拟 UDP Socket 层
  -> 每个玩家一个真实物理 UDP transport Socket
  -> 22333/UDP 鉴权云中继
  -> 对端 transport Socket
  -> 对端每个逻辑 Socket 的 FIFO 接收队列
  -> 合成 recvfrom 返回值交给对端 WE8.exe
```

该架构不使用：

- TAP、n2n、OpenVPN 或其他虚拟网卡。
- WinDivert、WFP 驱动或内核抓包驱动。
- Windows ARP、房间路由或系统虚拟 IP。
- 玩家侧 WE8 公网入站端口。

双方只维护一个发往云中继的 UDP 出站/NAT 映射。中心中继是可靠性基线，P2P
只能作为以后降低延迟和带宽成本的优化；P2P 失败必须能继续使用中继。

## 5. 虚拟 Socket 契约

### 5.1 生命周期与地址

Hook 跟踪 WE8 创建的每个 IPv4 UDP Socket：

- `bind(...:5739)` 只记录逻辑监听端口，不在物理网卡真实监听 `5739`。
- 未显式绑定的 Socket 在首次收发前分配 `49152-65535` 逻辑随机端口。
- `getsockname` 返回本玩家逻辑 IP 和当前 Socket 的逻辑端口。
- `closesocket` 删除映射并释放该 Socket 尚未消费的队列。
- 不属于虚拟表的句柄交回原始 Winsock，保持系统错误码。

逻辑 IP 只存在于 Hook、协议头和房间成员表中，不出现在 `ipconfig`、设备管理器、
ARP 表或 Windows 路由表中。

### 5.2 出站

每次 `sendto` 必须作为一个独立中继数据报发送，并保留：

```text
房间
来源逻辑 IP 和来源逻辑端口
目标逻辑 IP 和目标端口
广播标志
原始载荷长度与原始载荷
诊断序号
```

中继 transport 成功接收封装后，Hook 向 WE8 返回原始载荷长度。搜索广播发送给
同房间其他成员；逻辑单播只发送给目标逻辑 IP。

### 5.3 入站

transport 线程校验中继包后，根据目标逻辑端口查找本地 WE8 Socket，并把一个
完整数据报加入其 FIFO 队列。WE8 调用 `recvfrom` 时：

- 队列非空：返回原始载荷，并合成远端逻辑 IP 和原始逻辑源端口。
- 队列为空：返回 `SOCKET_ERROR / 10035`。
- 目标 Socket 已关闭或不存在：记录本地 `relay-drop`，不投递给其他 Socket。

`relay-drop` 这个历史字段名容易误解。它表示 DLL 收到中继包后无法加入目标
逻辑 Socket 队列，常见原因是 Socket 已关闭；它不等同于 Linux 中继丢包。

实现保留同步 `WSASendTo/WSARecvFrom` 的防御性兼容。当前已测试 WE8 没有使用
它们；重叠 I/O 当前也不属于已验证路径。

## 6. 中继协议 v2

P2 使用固定 `74` 字节头部，整数、地址和端口均为网络字节序：

```text
magic[4] = WNP2
version[1]
type[1] = register | data
flags[1] = broadcast
reserved[1]
room[32]
sourceIPv4[4]
sourcePort[2]
targetIPv4[4]
targetPort[2]
payloadLength[2]
sequence[4]
authTag[16] = HMAC-SHA256 前 16 字节
payload[n]
```

中继按 `(room, logical IP)` 保存玩家的真实 UDP endpoint，客户端每 2 秒注册一次，
30 秒无活动则淘汰。每个注册包和数据包必须通过 HMAC 校验；失败包直接丢弃。

当前 P2 使用一个双方相同的私有测试令牌。该令牌只适合验证，不是生产身份系统。
正式版本必须由平台签发短期房间/玩家凭证，并增加防重放、速率限制和带宽配额。
当前协议提供认证与完整性校验，但不加密 WE8 载荷。

### 7.2 已证实的时间线


客机发出的 `686` 包、`40,182` 字节在主机日志中精确收到：

```text
客机 sendto：686 包 / 40,182 字节
主机 recvfrom：686 包 / 40,182 字节
```

中继服务端同时记录：

```text
auth_drops=0
malformed_drops=0
```

这证明 P2 已经通过公网中心中继完成搜索、加入、接受和比赛建立，也证明上行
数据报在本次有效时间窗内完整到达主机。

### 7.3 尾段 `relay-drop` 的正确解释

客机日志尾部出现：

```text
46 个 relay-drop
合计 13,040 字节
目标逻辑端口全部为 63540
```

这 46 条全部出现在客机有效 Socket 活动停止后的日志尾部，表示晚到的主机数据
已经找不到仍可消费的客机逻辑 Socket。结合用户确认主机使用信号不好的移动热点，
本样本应归类为“不稳定网络或会话结束后的尾包”，不能据此认定 Linux 中继丢包，
也不能据此宣称客户端正常比赛期间发生了 46 次传输丢包。

同样，本样本没有完成规定时长的稳定比赛，因此只能得出：

- 云中继搜索成功。
- 云中继加入和接受成功。
- 比赛流量成功开始。
- 尚未完成公网长时间稳定性验收。

## 9. 诊断日志判读

每次测试必须同时保留主机和客机 JSONL，先按逻辑端口和数据长度对账：

1. 客机是否发出目标 `5739` 的 24 字节搜索包。
2. 主机是否收到同源端口 24 字节包并回复 136 字节。
3. 客机是否创建新的加入端口并发送 64 字节。
4. 主机是否从临时随机端口发出 84 字节接受包。
5. 客机是否从该临时端口收到 84 字节。
6. 比赛端口与主机 `5739` 是否开始持续双向交换。
7. 双方 `sendto` 与对端 `recvfrom` 的包数和字节数是否能在重叠时间窗对账。
8. `relay-drop` 是出现在有效比赛期间还是 Socket 关闭后的尾部。
9. 服务端 `auth_drops`、`malformed_drops`、`route_drops` 是否增长。

不能只看到一个错误字段就判断根因。必须先区分：游戏没有发送、客户端没有封装、
中继没有路由、对端没有收到，还是对端 Socket 已关闭后晚包到达。

## 10. 当前结论与生产缺口

### 10.1 已完成

- 已掌握该 WE8 构建的完整搜索、加入、接受与比赛 Socket 时间线。
- P1 已完成约 4 分钟真实双机无网卡比赛，双向对账一致、队列丢弃为 0。
- P2 已完成带 HMAC 鉴权的公网中心中继搜索、加入和开赛。
- 无网卡中继与现有 TAP/n2n、Docker 和 API 完全隔离。

### 10.2 尚未完成

- 信号稳定的异地网络至少 10 分钟双向比赛验收。
- Windows 10/11、防火墙开启、多实体网卡、其他 VPN 共存的测试矩阵。
- 平台签发的短期房间/玩家凭证。
- 防重放、限速、带宽配额、监控和容量规划。
- 断线重注册、会话关闭和晚包处理的明确状态机。
- 多中继节点、故障转移与区域调度。
- 产品平台内的房间成员分配、启动和日志上传集成。

### 10.3 下一轮正确验收方式

使用稳定网络的主客机，保持同一房间、同一测试令牌、不同逻辑 IP：

1. 双方从 GUI 启动 WE8。
2. 客机至少完成两次搜索并看到主机。
3. 客机加入，主机接受。
4. 比赛持续至少 10 分钟。
5. 双方正常退出后再结束日志。
6. 同时提交两份 JSONL，并对账有效时间窗内所有 `sendto/recvfrom`。

在长稳验收完成前，P2 的准确状态是“公网联机链路已打通”，不是“已经可以替换
现网生产平台”。现有 TAP/n2n 继续承担生产联机；无网卡版本在独立仓库继续成熟。
