# WEL 无虚拟网卡方案设计

## 1. 已确认的事实

来自成功的 TAP+n2n 诊断包，WE8 的局域网协议至少包含以下 UDP 语义：

| 阶段 | 来源 | 目标 | 关键点 |
|---|---|---|---|
| 搜索 | 客机逻辑 IP:随机端口 | 房间广播地址:5739 | 载荷完整保留，广播需扇出给同房其他成员 |
| 搜索回复 | 主机逻辑 IP:5739 | 客机原随机端口 | 必须回到发起搜索的准确 Socket |
| 加入/比赛 | 客机随机端口 | 主机逻辑 IP:5739 | 随机端口不能被简化为 5739 |
| 后续会话 | 双方逻辑 IP 和各自端口 | 对端逻辑 IP 和端口 | 不解析、不合并、不截断 WE8 UDP 载荷 |

玩家逻辑 IP 仍由平台服务端按房间唯一分配。无 TAP 只意味着 Windows 不再真的拥有 `10.222.x.x`，不意味着游戏不再需要看到这个逻辑地址。

## 2. 目标架构

```text
WE8.exe
  -> welnpttrace.dll（P0 只观测；后续升级为虚拟 Socket Hook）
  -> 本机 WEL 代理（localhost IPC）
  -> WEL 房间 UDP 中继（先中继，后续可增加 P2P）
  -> 其他玩家本机 WEL 代理
  -> 对端 WE8.exe
```

平台 API 负责鉴权、房间成员与逻辑 IP 分配。数据代理只根据逻辑五元组转发，不理解实况的游戏状态和操作。

## 3. 不可省略的虚拟化

不能只将搜索广播转发到服务端。最终 Hook 至少需要：

1. 记录每一个 WE8 UDP Socket 及其逻辑本地端口。
2. 拦截出站 `sendto`/`WSASendTo`，把目标地址和 UDP 载荷交给本机代理。
3. 将 `255.255.255.255:5739` 标记为房间广播，代理只投递给其他房间成员。
4. 将代理返回的包投递到目标逻辑本地端口对应的 Socket。
5. 在 `recvfrom`/`WSARecvFrom` 返回原载荷和伪造的对端逻辑 `sockaddr_in`。
6. 同步虚拟化 WE8 实际使用的“Socket 可读”通知方式。

第 6 项必须以 P0 trace 结果为准。若 WE8 使用 `select`，只 Hook `recvfrom` 不会让游戏知道队列中有包；若使用事件或异步 I/O，则需要分别支持。

## 4. 本机代理包协议草案

Hook 与本机代理之间使用独立协议，所有整数使用网络字节序：

```text
magic[4]       = "WNP1"
version[1]     = 1
flags[1]       = broadcast(1) | response(2)
headerLength[2] = 36
sessionId[8]
socketId[8]    = Hook 进程内 Socket 标识
sourceIPv4[4]
sourcePort[2]
targetIPv4[4]
targetPort[2]
payloadLength[2]
payload[n]
```

代理到房间中继的外层协议必须额外带上用户授权、房间 ID、重放保护和包序号。P0 不发送这种数据，协议将在 P1 与服务端一起固定。

## 5. 验收顺序

1. P0 trace 同时记录 `bind`、发送、接收及等待 API，不改变 LAN 测试结果。
2. P1 在同一台电脑的测试进程中复现广播和定向单播。
3. P2 两台电脑通过房间中继能够搜索、加入并稳定比赛 10 分钟。
4. P3 Windows 10/11 防火墙开启、多个实体/虚拟网卡共存时仍可用。
5. P4 只将 P2P 当作优化；中继必须始终可用。

## 6. 明确不做的事

- 不安装 TAP、OpenVPN、n2n、WinDivert 或其他内核包过滤驱动。
- 不添加系统路由、ARP 条目或虚拟 IP。
- 不解析比赛操作、比分或游戏状态。
- 不把单播会话强行合并为 `5739 -> 5739`。
